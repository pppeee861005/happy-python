 ## 故事一：凌晨兩點的事故記憶

  情境是凌晨兩點，系統突然出錯。你在頻道問：

  > 我們以前遇過這個錯誤嗎？

  Agent 隨即搜尋過去六個月的紀錄，整理出：

  - 類似事故發生過幾次
  - 當時的錯誤訊息
  - 每次的根本原因
  - 採用過的修正方法
  - 哪位成員最後處理過相關功能

  它還可以詢問你是否需要通知相關人員。

  這個故事的核心是 組織記憶。傳統團隊的經驗散落在聊天、文件、Issue 和某些人的腦中；Buzz 希望 Agent 能即時找回這些記憶，而且
  附上原始討論作為證據。

  重點不是 Agent「記得」，而是它找得到並能證明。

  ## 故事二：功能分支就是房間

  當你建立一個功能分支，Buzz 同時產生一個專屬房間。這個房間保存：

  - 為何需要這個功能
  - 相關程式 patch
  - CI 測試結果
  - Agent 的初步審查
  - 團隊成員的意見與 reaction
  - 最後是否合併的決定

  一般開發流程裡，需求可能在聊天軟體、程式碼在 GitHub、測試結果在 CI 平台、決定又在會議中。Buzz 想把這些資訊集中成一條完整紀
  錄。

  這個故事的核心是 決策脈絡：

  > 不只知道程式碼改了什麼，也知道為什麼改、誰檢查過，以及根據什麼證據合併。

  這應該是三個故事裡最具 Buzz 特色的一個。

  ## 故事三：會自己撰寫紀錄的發布流程

  當團隊建立一個版本標籤後，workflow 自動啟動：

  1. Agent 閱讀各專案頻道裡已合併的 PR。
  2. Agent 整理變更並撰寫發布說明。
  3. 草稿貼到頻道，等待人類檢查。
  4. 人類用 👍 reaction 核准。
  5. Workflow 正式發布版本。
  6. 每個步驟都經過簽署，而且可以搜尋。

  這並不是讓 AI 不受控制地自行發布，而是：

  > Agent 負責蒐集與準備，人類保留最後核准權。

  故事的核心是 可稽核的自動化。日後可以查到資料來自哪些 PR、Agent 寫了什麼、誰核准，以及何時發布。

  ## 三個故事其實是一條成熟路線

   故事        Buzz 保存的東西       Agent 的角色            人類的角色
  ━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━
   事故記憶    歷史與解決經驗        搜尋、整理證據          判斷與處置
  ──────────  ────────────────────  ──────────────────────  ────────────
   分支房間    開發與合併脈絡        修改、測試、初審        審查與決策
  ──────────  ────────────────────  ──────────────────────  ────────────
   自動發布    發布流程與核准紀錄    整理、產生草稿、執行    核准發布

  它們代表三個層次：

  1. AI 幫你找資料
  2. AI 和你一起完成工作
  3. AI 執行自動化，但人類保留控制權

  我認為這三個故事背後最重要的思想是：

  > Buzz 不是要讓 Agent 取代團隊，而是讓 Agent 的每個行動都進入團隊原本的權限、證據與審核制度。

  就你目前的學習階段，最適合先實作的是第一個「事故記憶」故事。它不需要讓 Agent 修改程式或進行發布，風險最低，卻能直接體驗
  Buzz「回答附證據」的核心價值。官方原文位於 Buzz README (https://github.com/block/buzz#three-little-stories)。
