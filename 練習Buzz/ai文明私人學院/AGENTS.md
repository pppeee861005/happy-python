## 專案定位

- 本專案的核心目標是運用 Buzz 的亮點，學習多人與多 Agent 協作，並思考未來的潛力與可能性。
- 「AI 文明私人學院」是多人與多 Agent 協作的實作與驗證案例，不是本階段的產品交付目標。
- 若案例的商業或產品需求與核心目標衝突，以協作學習與未來探索為優先。
- 不為了展示技術複雜度而增加功能。
- `AI文明私人學院_MVP_v0.1_交接包/` 提供練習情境與過往構想，不取代專案核心目標。

## 目標對齊

- 每項任務都應指出運用的 Buzz 亮點、要觀察的協作模式，以及可能揭示的未來潛力。
- 優先採用能快速操作、觀察與驗證的最小練習。
- 將 Buzz Canvas 視為核心學習介面，優先用於課程地圖、共同筆記、成果與 Agent 交接。
- 設計 Canvas 練習時，同時驗證人類桌面操作與 Agent 經由 MCP／CLI 的讀寫能力。
- 一個協作實驗應盡量留下 Buzz 亮點、參與者與分工、最小案例、驗證結果、Canvas 狀態、反思及未來可能性。
- 無法說明如何增進協作學習或未來探索的功能，暫不實作。

## 現階段原則

- 先運用 Buzz 進行協作實驗、驗證與記錄，再擴充工程規模。
- 現成工具能完成的事情，不重複開發。
- 沒有真實、反覆、可驗證的需求，不新增 Agent 或複雜架構。
- 不先建立網站、App、資料庫、Vector DB、MCP 或複雜 Multi-Agent orchestration。
- 每次改動應能回答：學到了什麼、驗證了什麼，或替學員創造了什麼價值。

## 專案結構

- `readme.MD`：專案入口、協作探索核心與主題說明。
- `AI文明私人學院_MVP_v0.1_交接包/`：產品理念、文明憲法、服務流程、實驗與決策紀錄。
- 目前沒有應用程式碼、依賴或自動化測試。
- 若日後加入 Python 實作，使用 `src/` 放模組、`tests/` 放 pytest 測試、`assets/` 放範例素材、`docs/` 放學習筆記。

## 開發與驗證

- 不要把尚未設定的指令描述成可用的專案指令。
- 新增可執行功能時，同步在 `readme.MD` 記錄確切的安裝、執行與測試方式。
- Python 採四格縮排、PEP 8、公開函式型別提示；測試檔命名為 `test_<module>.py`。
- 測試應 mock 網路與外部 AI 服務，不應預設需要 API 金鑰、麥克風、模型下載或私人錄音。

## 安全與版本控制

- 不提交 API 金鑰、Token、`.env`、私人錄音、模型下載、虛擬環境或生成的逐字稿。
- 引入環境變數時，提供已去除敏感資料的 `.env.example`。
- 保留使用者既有且與任務無關的修改。
- Commit 使用簡潔、祈使語氣的繁體中文，或一致採用 `feat:`、`fix:`、`docs:`、`refactor:` 等前綴。
