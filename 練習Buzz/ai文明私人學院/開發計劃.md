# 開發計劃｜以 AI 文明私人學院探索人類與多 Agent 協作

## 一、計劃目的

本專案的核心目標是：**運用 Buzz 的亮點，學習多人與多 Agent 協作，並思考未來的潛力與可能性。**

「AI 文明私人學院」是貫穿各階段的實作主題，用來驗證多人與多個 AI Agent 如何在 Buzz 的同一個工作空間中理解問題、分工、交接、決策、執行任務並留下可追蹤的成果。

本計劃不以快速完成完整產品為目標，而是把 Buzz 的亮點拆成可操作、可驗證的協作實驗，並在每次實驗後記錄限制、啟發與未來可能性。

## 二、目標優先順序

1. 運用並理解 Buzz 的核心亮點。
2. 建立可重複驗證的多人—多 Agent 協作流程。
3. 使用「AI 文明私人學院」提供真實的協作情境。
4. 從實驗中思考未來的服務、組織與文明可能性。
5. 根據驗證結果與真實需求，才決定是否擴大產品或架構。

如果產品構想與核心目標衝突，以協作學習與未來探索為優先。

## 三、開發原則

- 一次只學習一項主要能力。
- 先完成一個 Agent 的閉環，再考慮多 Agent。
- 每個主要課程都應實際使用 Buzz Canvas，而不是只停留在聊天。
- 每個單元都要留下概念、最小範例、驗證結果與反思。
- 優先使用 Buzz 已經能運作的功能，不把願景當成現成功能。
- 關鍵決策與外部行動保留人工核准。
- 不因技術有趣而提前建立網站、App、資料庫或複雜 orchestration。
- 現成工具能完成的事情，不重複開發。

## 四、合作方式

- 使用者親自操作 Buzz：安裝、啟動、點擊、輸入、建立頻道與測試流程。
- Codex 負責教學：說明每一步的目的、提供最小指令、解讀畫面與結果、安排下一步。
- 每次只推進一個主要操作，使用者回報結果後才進入下一步。
- 不把使用者的操作假設成已完成；所有里程碑都以使用者回報的實際畫面或結果為準。

## 五、核心實作情境

在 Buzz 中建立「AI 文明私人學院」社群，讓人類與 AI 導師共同接待學員。

建議初始頻道：

- `學員接待`：學員與 AI 導師開始對話；Canvas 保存本次課程地圖與下一步。
- `導師工作室`：整理教學策略；Canvas 保存可重用的教學設計。
- `知識查證`：討論待查證事項；Canvas 保存已確認的結論與來源。
- `人工核准`：處理需要人類確認的行動；Canvas 說明核准標準與目前狀態。
- `學習與開發記錄`：保存 Buzz 實驗；Canvas 維護目前進度、成果與待辦。

第一個 Agent 僅建立「AI 導師」。其他角色先作為同一個 Agent 的思考職能，不立即建立獨立 Agent。

## 六、Buzz Canvas 的課程定位

Canvas 是本課程的核心介面，不是課後附加功能。

每一個學習單元都盡量完成以下 Canvas 循環：

```text
人類在 Canvas 設定目標
→ Agent 讀取 Canvas 理解任務
→ 人類與 Agent 在頻道中討論與執行
→ Agent 提議或寫入成果
→ 人類回讀、修正或核准
→ Canvas 留下最新共同狀態
```

使用原則：

- 頻道訊息保存討論過程，Canvas 保存目前有效的共同結論。
- Canvas 內容要短、清楚、能被下一位人類或 Agent 接手。
- 不把 API 金鑰、私鑰、Token 或敏感個資寫入 Canvas。
- Agent 寫入後由人類回讀重要內容，不把自動更新視為天然正確。
- 同時練習桌面端操作，以及 MCP／CLI 的 Agent 讀寫方式。

## 七、協作實驗與開發階段

### 階段 0：確認學習基線

要學的 Buzz 能力：區分目前可用功能、開發中功能與願景。

任務：

- 確認準備使用的 Buzz 版本與安裝方式。
- 確認本機環境、必要工具與啟動條件。
- 記錄哪些能力目前可以實際操作。
- 建立第一次開發記錄。

完成判準：

- 能說明 Buzz 的定位與六項主要亮點。
- 有明確的版本、環境與啟動方式紀錄。
- 不把尚未完成的官方願景列為可用功能。

### 階段 1：建立人類與 Agent 的共同空間

對應亮點：人類與 Agent 在同一個工作現場。

任務：

- 啟動或連接一個可使用的 Buzz relay。
- 建立「AI 文明私人學院」社群。
- 建立最小必要頻道。
- 讓一位人類成員進入並完成頻道訊息互動。

完成判準：

- 能進入社群並看到頻道。
- 能發送、接收及搜尋一則測試訊息。
- 留下操作步驟與驗證證據。

### 階段 2：讓 AI 導師成為正式成員

對應亮點：Agent 是成員，不只是工具。

任務：

- 建立 AI 導師的獨立身分。
- 只授予必要的頻道成員資格與工作範圍。
- 讓 AI 導師在 `學員接待` 頻道回應第一則學習訊息。
- 觀察 Agent 的訊息是否具有可辨識的身分與紀錄。

最小教學任務：

> 學員不知道要問什麼時，AI 導師提供五個初始話題，並一次只引導一個主要概念。

完成判準：

- 人類與 AI 導師能在同一頻道互動。
- Agent 的身分、訊息與行動可以區分和追蹤。
- Agent 不具備超出任務所需的權限。

### 階段 3：用 Buzz Canvas 建立共享課程地圖

對應亮點：頻道共享文件，以及人類與 Agent 的共同工作面。

任務：

- 在 `學員接待` 頻道建立 Canvas。
- 由人類寫入本次課程目標、已知程度與完成條件。
- 讓 AI 導師讀取 Canvas，並用自己的話說明任務。
- 讓 AI 導師更新課程摘要、學到的內容與下一個小步驟。
- 由人類回讀並修正，驗證共同編輯流程。

完成判準：

- 人類可在桌面端讀寫同一份 Canvas。
- Agent 可透過目前版本支援的 MCP／CLI 介面讀取與更新 Canvas。
- Canvas 在重新開啟後仍保存最新共同狀態。
- 能辨識 Canvas 更新的作者與事件紀錄。

### 階段 4：讓 Agent 使用工具完成任務

對應亮點：透過 ACP、MCP 與 agent-first CLI 組合能力。

任務：

- 理解 Buzz 中 ACP、MCP 與 `buzz-cli` 的角色。
- 先以 Canvas 讀寫作為第一個最小工具能力，再練習讀取教材或更新其他學習紀錄。
- 讓 AI 導師完成一次「收到需求 → 使用工具 → 回報結果」的閉環。
- 保留完整輸入、工具行動、輸出與錯誤紀錄。

完成判準：

- 能解釋 Agent、協定與工具之間的邊界。
- 至少完成一次可重複的工具呼叫。
- 失敗時能從紀錄定位問題，而不是只重試。

### 階段 5：建立可追蹤的事件與決策鏈

對應亮點：統一且可搜尋的事件紀錄。

任務：

- 完成一次「Canvas 設定目標 → 學員提問 → Agent 回應 → 工具行動 → Canvas 更新 → 人類確認」流程。
- 搜尋並回讀該次流程的對話、結果和核准紀錄。
- 驗證是否能回答誰、何時、根據什麼、做了什麼及結果為何。

完成判準：

- 能從 Buzz 還原一次完整任務的前因後果。
- 關鍵決策不只存在於個人記憶或外部筆記。
- 驗證證據寫入 `開發記錄.md`。

### 階段 6：加入人工核准的工作流程

對應亮點：可執行工作流程，同時保留人類在迴路中。

開始前先確認目前使用版本是否已完整支援 approval gate。若尚未支援，改用明確的人工 reaction 或頻道確認，再由人類執行 Canvas 正式更新，並把這項限制記錄下來。

任務：

- 選擇一個低風險觸發方式，例如訊息或 reaction。
- 建立最小工作流程：觸發、Agent 處理、人工核准、結果發布。
- 測試正常流程、拒絕流程與失敗流程。

建議情境：

> AI 導師產生本次學習摘要，經人類核准後才更新正式課程 Canvas。

完成判準：

- 未核准時不執行正式寫入或外部行動。
- 核准與拒絕都留下可搜尋紀錄。
- 失敗不會造成無限制重試或不明確狀態。

### 階段 7：評估是否需要多 Agent

對應亮點：多 Agent 協作，但由真實需求決定角色出生。

進入條件：

- 單一 AI 導師已完成前述閉環。
- 同一類工作重複出現。
- 有證據顯示拆分角色能提高品質、安全或效率。

候選角色：

- Scout：查找最新且相關的 AI 資料。
- Observer：判斷學員理解與興趣。
- Planner：選擇下一個最有價值的小步驟。

任務：

- 只拆出一個最有需要的角色。
- 比較拆分前後的品質、成本、時間與可追蹤性。
- 若沒有明顯改善，合併或移除該角色。

完成判準：

- 有資料支持新增 Agent，而不是只有想像。
- 每個 Agent 的身分、權限、輸入與責任清楚。
- 人類可以理解並回溯 Agent 之間的交接。

## 八、課程安排

| 課次 | 主題 | Canvas 實作 | 完成成果 |
|---|---|---|---|
| 第 1 課 | Buzz 定位、版本與環境 | 準備「Buzz 學習地圖」內容，成功啟動後放入 Canvas | 能區分現成功能與願景 |
| 第 2 課 | 社群、頻道與人類協作 | 建立頻道 Canvas 並手動更新 | 一個可回讀的共同工作空間 |
| 第 3 課 | Agent 身分與權限 | 在 Canvas 定義 AI 導師責任 | AI 導師完成第一次接待 |
| 第 4 課 | Buzz Canvas 共編 | 人類設定目標、Agent 讀寫、人工修正 | 一次完整 Canvas 協作循環 |
| 第 5 課 | ACP、MCP 與 `buzz-cli` | 用 Agent 介面讀寫 Canvas | 可重複的工具呼叫證據 |
| 第 6 課 | 事件、搜尋與稽核 | 回讀 Canvas 更新與相關討論 | 還原完整工作與決策鏈 |
| 第 7 課 | 工作流程與人工核准 | 核准後才更新正式課程 Canvas | 正常、拒絕與失敗紀錄 |
| 第 8 課 | 多 Agent 評估 | 用 Canvas 交接一項真實任務 | 有對照資料的拆分決策 |

每一課開始時讀取 Canvas 的「目前狀態」，結束時更新「本次成果、未解問題、下一步」。因此 Canvas 同時是課程入口、共同筆記與交接文件。

## 十、每個協作實驗的交付格式

每完成一個協作實驗，至少留下：

1. 本次運用的 Buzz 亮點。
2. 參與的人類、Agent、分工與交接關係。
3. 最小操作或程式範例。
4. 實際執行方式。
5. 成功或失敗的驗證證據。
6. 遇到的問題與解法。
7. 參與者能否根據紀錄重新理解、接手與重做。
8. 下一個最小步驟。
9. Canvas 開始與結束時的狀態變化。
10. 本次實驗揭示的未來潛力、限制或新可能。

詳細過程統一記錄於 `開發記錄.md`。

## 十一、目前不做

- 不以完成商業化 AI 家教平台作為近期成功標準。
- 不先做會員、付款、CRM 或完整後台。
- 不先建置網站、App、Vector DB 或複雜資料庫。
- 不一次建立 Guide、Scout、Observer、Planner、Evolution 五個獨立 Agent。
- 不在沒有驗證需求前建立複雜 Multi-Agent orchestration。
- 不把 Agent 數量、Token 數或回答數當成協作成果。

## 十二、近期下一步

下一個開發回合只做階段 0：

1. 選定 Buzz 的使用方式：安裝封裝版本，或從原始碼啟動。
2. 記錄 Buzz 版本與 Windows 環境條件。
3. 成功啟動或連接 relay。
4. 將實際指令、畫面或輸出寫入 `開發記錄.md`。

完成階段 0 後，才開始建立「AI 文明私人學院」社群與頻道。
