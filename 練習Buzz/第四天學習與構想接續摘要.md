- 長期、固定且會反覆出現的一類工作，應建立 **Channel**。

## 今日補充的安全觀念

- DM 只是限制可見對象，不代表可以傳送任何機密。
- 密碼、Token、API Key 與信用卡資料不應傳給 Agent。
- 個資只提供完成任務所需的最少部分，能匿名時優先使用代稱。
- Agent 必須先有權進入 Channel；加入後仍應使用正確的 `@名稱` 明確指派工作。

## 今天學會的 Buzz 觀念

- Community 是整個虛擬公司或工作空間。
- Channel 是部門、專案或長期重複出現的業務空間。
- Message 是 Channel 裡的一件新任務或新話題。
- Thread 用來延續同一件任務的追問、修正與結論。
- DM 適合私人、臨時或不宜公開的交流。
- Agent 加入 Channel，代表它有權看見與參與內容。
- 使用 `@Agent名稱`，才是明確要求該 Agent 處理及回答。
- 同時請多個 Agent 回答，可以在同一則 Message 中逐一 `@` 它們，並要求所有答案留在同一個 Thread。

## 本機操作與安全

- 如果 Agent 執行於本機並擁有檔案或命令工具，其他 Channel 成員可能透過 `@Agent` 要求它操作本機。
- 能操作本機的 Agent 不應放在任何人都可加入的公開 Channel。
- 公開服務 Agent 與私人營運 Agent 應分開。
- 私人營運 Agent 只應存取指定工作資料夾，且重要寫入、刪除及外部操作需要主人批准。
- 核心原則：`@Agent` 代表要求 Agent 工作，不代表下令者一定是電腦主人。

## 今天形成的核心構想：0 人公司

Buzz 的 Channel 不只是聊天室，可能成為一間微型公司的辦公室、服務櫃台與工作紀錄中心。

> 一個 Channel，就是一間可以運作的微型公司；一群 Agent，就是它的數位團隊。

0 人公司不是完全沒有人，而是日常工作主要由多個 Agent 完成，人類負責目標、授權、監督、專業覆核與責任承擔。

Buzz 可能成為「AI 團隊即服務」或「Agent Team Store」的基礎平台。

## 0 人公司的最小部門

1. 接待 Agent：了解客戶需求，引導客戶進入正確服務。
2. 業務 Agent：介紹商品、推薦方案並回答購買問題。
3. 交易 Agent：確認訂單、付款狀態及服務權限，但不直接接觸信用卡資料。
4. 內容 Agent：執行知識服務並交付成果。
5. 人類專家：在法律、財務、醫療或重大金額等高風險案件中進行最終覆核。

## 初步商業流程

```text
客戶進入網站
→ 接待與導購
→ 選擇知識商品
→ 透過金流服務付款
→ 系統確認訂單與權限
→ 客戶進入指定 Buzz Channel／服務介面
→ 多 Agent 團隊執行任務
→ 人類必要時覆核
→ 在 Thread 中完成交付與修改
```

## Buzz 與網站的角色

- 網站是 0 人公司的公開店面，負責商品介紹、會員、訂單與付款。
- Buzz 是公司的內部作業系統，負責 Channel、Agent 協作、Thread 工作紀錄及服務交付。
- 初期可在付款後邀請客戶進入私人 Buzz Channel。
- 中期可建立網站聊天介面，透過 Buzz Relay 或 API 將任務送入 Channel。
- 長期可開發可嵌入網站的 Buzz Widget，讓顧客在網站直接呼叫多 Agent 團隊。

## 目前看見的技術缺口

- Buzz 尚不能被假設為已有完整購物車與金流系統。
- 陌生網站訪客安全地只進入單一 Channel 並發言，仍需要更完整的訪客權限設計。
- 不能直接假設使用 iframe 就能安全地把完整 Buzz 嵌入公開網站。
- 需要設計顧客身分、訂單權限、Agent 工具權限、資料隔離及操作批准。

## 商業模式想法

- 免費體驗：單一 Agent 簡單回答。
- 基礎方案：多 Agent 分工完成分析。
- 進階方案：加入交叉辯論、風險檢查與正式報告。
- 專業方案：加入合格人類專家覆核。
- 訂閱方案：每月固定額度、定期報告或持續監測。
- 點數或虛擬貨幣可以作為交易工具，但真正的商品是可重複、可信任的多 Agent 工作流程。

## 建議的下一步

先不要急著建立虛擬貨幣或大型市集，先驗證：

> 顧客是否願意付費，請一支多 Agent 團隊完成一項明確的知識服務？

第一個最小可行原型可選擇「都更成本初步評估」：

- 一個簡單商品頁。
- 一種明確服務。
- 一個付款連結。
- 一個私人 Buzz Channel。
- 接待、成本試算、風險檢查及報告統整 Agent。
- 一位真人負責最終品質確認。
