# AI 社群經營 Channel 核心文件

## 唯一最高原則

> **最重要的是好玩。**

這個 Channel 的所有設定、文件、Agent、規則、故事與技術，都必須服務「參與者是否真的玩得開心」。

世界觀完整、技術先進、角色設定深刻或故事結構漂亮，都不能取代好玩。如果一項設計很精巧，卻降低互動、拖慢節奏或讓玩家失去參與感，就應修改或刪除。

## 核心手段

> **盡可能創造大量且有意義的人類與多 Agent 互動。**

這裡的目標不是讓玩家觀看 AI 表演，也不是讓單一 Agent 陪玩家聊天，而是讓多個不同意志同時存在、互相影響：

- 玩家與 Agent 對話。
- 玩家同時與多名 Agent 周旋。
- Agent 主動找玩家談話。
- Agent 彼此爭吵、合作、試探、欺騙或結盟。
- 玩家因 Agent 的行動而改變計畫。
- Agent 因玩家的選擇而改變關係與立場。
- 多名玩家可以合作，也可以產生意見衝突。
- 一次互動能自然引發下一次互動與新局勢。

互動數量不是唯一目標。沒有後果的洗版、重複附和與五名 Agent 輪流說相同內容，不算有效互動。

## 平台目標：展現 Buzz 的亮點

這個 Channel 不只是把一般 AI 聊天搬進 Buzz，而要設計出「只有多人、多 Agent 共享房間時才特別好玩」的體驗。

Buzz 的功能不應以教學或功能表展示，而應自然成為遊戲的一部分。玩家應在遊玩中感受到：

- **Agent 是房間成員：**每名 Agent 有自己的身分、立場、記憶與行動，不是同一個 AI 換五種語氣。
- **多人與多 Agent 同場：**任何一句話都可能同時改變多個人與角色的判斷。
- **自由召集角色：**玩家可透過 `@Agent` 指名質問、求助或同時召集多方對質。
- **共同歷史持續累積：**Channel 訊息保留承諾、謊言、衝突與選擇，之後可以被角色重新引用。
- **共享世界資料：**Canvas 承載穩定的世界規則與公開狀態，Channel 則承載正在發生的事件。
- **不同資訊範圍：**共同 Channel、個別 Agent 設定與主持人資料形成公開資訊、私人祕密與世界真相。
- **持續運作的世界：**事件、訊息與喚醒機制讓 Channel 不只是一次性問答，而是一個能繼續發展的場所。
- **人類保有主導權：**Agent 能主動貢獻，但玩家的介入會真實改變關係、目標與故事方向。

### 應優先呈現的 Buzz 體驗

1. **一則訊息喚醒多個不同角色**

   玩家同時 `@` 兩至三名 Agent，得到互相衝突、彼此回應的反應，而不是數份互不相干的答案。

2. **角色記得 Channel 裡真正發生過的事**

   Agent 會引用玩家先前的承諾、謊言、幫助與羞辱，使 Channel 歷史成為遊戲世界的記憶。

3. **Agent 彼此是關係，而不是工具集合**

   奧德修斯可以命令埃佩奧斯；涅俄普托勒摩斯可以公開反駁；玩家則能介入、選邊或破壞兩人的關係。

4. **共享資訊與私人動機同時存在**

   所有人看到同一個聲響值與環境，但每名 Agent 因自己的祕密作出不同選擇。

5. **Channel 在一場遊戲後仍有價值**

   完整對話能成為故事紀錄、試玩資料與下一次局勢的起點，而不是遊戲結束後即失去意義。

### 不應採用的展示方式

- 為了證明有五名 Agent，強迫五名 Agent 每次都輪流發言。
- 把 Canvas 當成長篇說明書，要求玩家先讀完才能開始。
- 讓 Agent 不斷重述 Buzz 功能或解釋自己是 AI。
- 為了展示自動化而犧牲節奏、製造洗版或無限互相觸發。
- 使用很多平台功能，卻沒有產生新的選擇、關係或樂趣。

判斷 Buzz 功能是否值得加入時，應詢問：

> 玩家會因為這個功能，與更多不同意志產生更有趣的互動嗎？

## 好玩的判斷標準

一段遊戲若符合越多下列現象，就越接近核心目標：

- 玩家主動想問某名 Agent：「你到底在隱瞞什麼？」
- 玩家會在多名 Agent 之間選邊、協調或挑撥。
- Agent 對同一件事提出不同且合理的立場。
- 玩家提出設計文件沒有預料到的辦法。
- 一個選擇同時改變危機、信任與角色關係。
- 玩家會笑、緊張、懷疑、後悔或期待下一個回應。
- 即使計畫失敗，形成的新局勢仍讓人想繼續玩。
- 遊戲結束後，參與者想討論「如果當時做另一個選擇會怎樣」。

如果玩家只是等待主持人公布答案、依序閱讀 Agent 台詞，或尋找唯一正解，就需要重新設計。

## Agent 設計原則

每名 Agent 都應具有：

1. **清楚而不同的個性：**玩家能從語氣與選擇辨認是誰在說話。
2. **可理解的慾望：**Agent 必須真心想得到、避免或保護某些事物。
3. **不完全公開的資訊：**讓玩家有理由追問、試探與交換情報。
4. **與其他角色的摩擦：**至少能與兩名角色形成衝突、依賴或交易。
5. **改變立場的可能：**Agent 會記住玩家的承諾、傷害與幫助，不應永遠照預設劇本行動。
6. **主動行動能力：**Agent 不只回答問題，也會在局勢相關時介入、阻止、邀請、警告或冒險。

Agent 可以說謊、拒絕或背叛，但不可毫無動機地隨機搗亂。謊言應能被懷疑，背叛應有累積過程，衝突應帶來新的選擇。

## 多 Agent 互動原則

- 優先製造「不同角色都在乎，但理由不同」的局勢。
- 主持人可同時 `@` 兩至三名立場相衝的 Agent。
- Agent 回應時可以直接質問或阻止其他 Agent，不必永遠只對主持人說話。
- 每名 Agent 不必對每則訊息發言；只有能增加選擇、情緒、資訊或後果時才介入。
- 避免所有 Agent 同時同意玩家。合作也應保留不同代價與動機。
- 避免長篇獨白。短而有方向的回應更容易讓其他人接手互動。
- 讓沉默、拒絕回答與私下接觸也能成為可追查的行動。

## 玩家地位

玩家不是觀眾，也不是等待選項的解題者。

玩家可以隨時：

- 描述自己的行動。
- `@` 一名或多名 Agent。
- 質問、安撫、欺騙、威脅、交易或命令角色。
- 與其他玩家合作、競爭或對立。
- 忽略主持人的暗示。
- 創造規則與事件庫沒有列出的方案。
- 放棄、破壞或改寫原定任務。

世界必須回應玩家的合理行動。不能因玩家偏離預定故事，就讓所有嘗試無效或強迫他們返回原路。

## 主持人職責

主持人的工作不是講完準備好的故事，而是讓互動持續產生值得玩的後果。

主持人應：

- 以環境、危機與資訊差點燃對話。
- 自由喚醒與當前局勢最相關的 Agent。
- 在不同玩家與 Agent 之間建立交叉關係。
- 記住承諾、祕密、傷勢、敵意、信任與未完成的交易。
- 讓玩家的辦法有效，同時產生合理代價。
- 在互動停滯時加入壓力，而不是直接公布答案。
- 在訊息過多時收束焦點，避免五名 Agent 同時洗版。
- 讓失敗改變世界，不把失敗當成遊戲結束。

主持人每次準備加入事件前，應先問：

> 這件事會讓哪些人與哪些 Agent 開始互動？他們會因此面臨什麼新選擇？

如果答案只是「讓故事照大綱繼續」，就不應急著加入。

## 文件與規則的地位

- 規則用來製造選擇與後果，不是限制創意。
- 角色設定用來產生一致而有張力的行動，不是固定台詞。
- 事件庫是主持素材，不是待辦清單。
- 劇情架構是可能局勢，不是必經軌道。
- 數值是世界回應的提示，不是遊戲樂趣本身。
- 技術是承載互動的工具，不是開發目的。

當文件內容與現場樂趣衝突時，優先保留樂趣，再於遊戲後修正文件。

## 應避免的情況

- 五名 Agent 輪流發表相似意見。
- Agent 只在被點名後回答，從不主動改變局勢。
- 主持人連續發布事件，玩家沒有時間互動。
- 角色知道自己不應知道的其他角色祕密。
- 長篇世界觀說明中斷遊戲節奏。
- 玩家只能從主持人提供的選項中選擇。
- 一次判定消除所有矛盾，沒有留下新問題。
- 為了維持預定結局而否定合理行動。
- 把「訊息很多」誤認為「互動很多」。
- Agent 互相觸發無限對話，讓玩家無法介入。

## 開發優先順序

每次新增功能或內容時，依序判斷：

1. 它會不會讓遊戲更好玩？
2. 它會不會增加人類與多 Agent 的有效互動？
3. 它是否展現 Buzz 作為多人、多 Agent 共享空間的獨特價值？
4. 它會不會讓玩家擁有更多有後果的選擇？
5. 它會不會讓 Agent 之間產生更鮮明的關係？
6. 它是否容易理解並能在 Channel 中實際運作？
7. 最後才考慮設定是否更完整、系統是否更複雜。

若前四項沒有明確改善，就不應因為功能看起來新奇而加入。

## 試玩檢查

每次試玩後記錄：

- 每名玩家主動與幾名 Agent 互動？
- 是否有玩家同時召集多名 Agent？
- Agent 之間是否產生真正影響局勢的互動？
- 哪名 Agent 最常被忽略？為什麼？
- 哪段對話最好玩？好玩的原因是什麼？
- 哪段時間玩家只能等待？
- 哪些 Agent 回應重複、過長或沒有後果？
- 玩家是否創造了預料外的方案？世界有沒有合理回應？
- 玩家是否想繼續下一個局勢？

試玩成功不以故事有沒有照計畫完成判斷，而以參與者有沒有產生投入、選擇、關係與「還想再玩」的感覺判斷。

## 最終檢核句

任何開發決定都回到兩個問題：

> **這樣真的更好玩嗎？**
>
> **這樣會讓更多人與更多 Agent 產生有意義的互動嗎？**
>
> **這樣有讓玩家感受到 Buzz 的獨特亮點嗎？**

如果前兩個答案不明確，就先不要做；第三個答案不明確，就思考是否只是把普通聊天室搬進 Buzz。
