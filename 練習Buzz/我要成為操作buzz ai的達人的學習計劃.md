# 我要成為操作 Buzz AI 達人的學習計劃

## 目標

每天學習 1 小時，以實際操作為主，逐步成為能獨立使用、管理與判斷 Buzz 協作狀態的熟練操作者。

本計畫不 clone 原始碼、不研究底層架構、不準備開發工具鏈。重點是精通 Buzz 的真正價值：讓人類與 AI Agent 在相同的 Community 中，以清楚的身分、權限、任務、對話脈絡及操作紀錄共同工作。

完成後應能：

- 規劃並管理 Community、Channel 與 Thread。
- 建立、設定及管理不同職責的 Agent。
- 寫出清楚、可執行、可驗收的 Agent 任務。
- 判讀 Reaction、執行狀態、文字回覆及 Harness Log。
- 管理 Agent 的上下文、頻道範圍與安全邊界。
- 從搜尋及稽核紀錄還原任務與決策過程。
- 設計由人類決策、Agent 執行的多 Agent 協作流程。

## 每天固定節奏

- **10 分鐘複習：** 用自己的話重述昨天最重要的觀念。
- **40 分鐘操作：** 在 Buzz 中完成當天任務，觀察畫面、狀態與紀錄。
- **10 分鐘記錄：** 寫下操作結果、判斷依據、錯誤與下一個問題。

每一天都用三個問題驗收：

1. 我實際做了什麼？
2. 我觀察到什麼證據？
3. 我能根據證據做出什麼判斷？

## 第一階段：建立操作基本功

### 第 1 天：認識 Buzz 的精髓

- 分辨 Buzz、一般 AI 聊天視窗及傳統團隊聊天室。
- 認識 Community、Channel、Thread 與 Agent。
- 用自己的話說明「人類與 Agent 共用工作空間」的意義。

**完成條件：** 能在三分鐘內向別人解釋 Buzz 是什麼，以及它適合解決什麼問題。

### 第 2 天：安裝並建立第一個 Agent

- 安裝 Buzz Windows 桌面版。
- 建立身分、Community 與測試頻道。
- 建立 Fizz，設定 Codex runtime，確認狀態為 `running`。
- 觀察訊息、Reaction、回覆與 Harness Log。

**完成條件：** Fizz 能在指定頻道接收任務並以自己的身分回覆。此日已完成。

### 第 3 天：精通 Agent 設定與狀態判讀

- 逐項查看 Fizz 的名稱、指令、Runtime、Provider、Model、Effort 與管理者。
- 傳送一個簡單、可驗收的任務。
- 觀察 `👀`、`💬`、`running`、文字回覆與 Harness Log 各自代表什麼。
- 練習區分「已收到」「處理中」「已回覆」與「已正確完成」。

**完成條件：** 能根據畫面與紀錄判斷 Agent 現在處於哪個階段，而不是只憑 Reaction 猜測。

### 第 4 天：頻道與討論串的正確用法

- 建立兩個用途不同的測試 Channel。
- 為 Channel 寫出明確名稱與說明。
- 將一項任務放入 Thread，避免主頻道混亂。
- 比較主頻道訊息與 Thread 回覆的脈絡差異。

**完成條件：** 能判斷新話題應建立 Channel、另開訊息或使用 Thread。

### 第 5 天：寫出可執行的 Agent 任務

- 使用「目標、背景、限制、輸出格式、完成條件」五部分寫任務。
- 分別送出一個模糊任務及一個清楚任務。
- 比較 Fizz 的回覆品質與追問次數。

**完成條件：** 能寫出 Agent 不必猜測、結果可以人工驗收的任務。

### 第 6 天：控制上下文

- 測試 Agent 能否理解同一 Thread 的前文。
- 在不同 Channel 問相似問題，觀察上下文是否混用。
- 練習在新任務中補齊必要背景，不假設 Agent 記得其他對話。

**完成條件：** 能判斷 Agent 知道什麼、不知道什麼，以及何時必須補充背景。

### 第 7 天：第一階段實戰

- 建立一個小型工作主題與專用 Channel。
- 交給 Fizz 一項包含明確成果的任務。
- 使用 Thread 追問、修正並完成驗收。
- 從狀態與紀錄說明任務如何完成。

**完成條件：** 不靠逐步教學，獨立完成一次有清楚脈絡的 Agent 協作。

## 第二階段：任務管理與安全協作

### 第 8 天：Agent 身分與責任邊界

- 分辨管理者、Buzz Agent 身分與背後 Runtime。
- 解釋為什麼使用 Peterhuang 的 Codex 執行，訊息仍顯示為 Fizz。
- 檢查哪些動作由人做、哪些動作由 Agent 做。

**完成條件：** 能從身分與紀錄正確判斷一項操作是誰執行的。

### 第 9 天：權限與最小範圍

- 建立測試用私人 Channel。
- 檢查 Agent 是否為頻道成員，以及能看到哪些內容。
- 只提供完成任務真正需要的存取範圍。

**完成條件：** 能讓 Agent 完成指定工作，同時避免提供不必要的資訊或權限。

### 第 10 天：安全操作

- 辨識私鑰、API Key、Token、個人資料及私人錄音。
- 練習用假資料描述設定問題。
- 檢查筆記與截圖是否意外包含敏感資訊。

**完成條件：** 能在求助與除錯時提供足夠資訊，同時不洩漏秘密。

### 第 11 天：搜尋與找回脈絡

- 建立一組帶有特殊關鍵字的測試訊息。
- 搜尋任務、人物、結論與相關討論串。
- 請 Agent 摘要搜尋到的內容，再人工核對。

**完成條件：** 能從 Buzz 找回一項舊任務的問題、過程與結論。

### 第 12 天：證據導向的回答

- 要求 Agent 回答時指出依據的訊息或 Thread。
- 區分可直接確認的事實、合理推論及未知事項。
- 找出一個缺乏證據的回答並要求修正。

**完成條件：** 不因 Agent 說得流暢就相信，而能檢查其依據。

### 第 13 天：修正、拒絕與人工核准

- 讓 Agent 提交草稿，而不是直接視為完成品。
- 練習要求修改、拒絕不合格成果及明確核准。
- 確認每一次決策都留在同一個 Thread。

**完成條件：** 能讓 Agent 執行、人類決策，並留下清楚的核准紀錄。

### 第 14 天：第二階段實戰

- 指派一項資訊整理任務。
- 限制 Agent 的範圍及輸出格式。
- 核對證據、要求一次修正，最後人工核准。

**完成條件：** 完成一次安全、有證據且有人類驗收的任務。

## 第三階段：故障判斷與穩定操作

### 第 15 天：建立正常狀態基準

- 記錄正常執行時的 Agent 設定、狀態、Reaction、回覆順序與日誌特徵。
- 建立自己的「正常運作檢查表」。

**完成條件：** 遇到異常時知道應與什麼正常狀態比較。

### 第 16 天：Agent 沒有回覆時怎麼辦

- 依序檢查頻道、Agent 成員資格、`running` 狀態、Runtime、Provider 與 Harness Log。
- 分辨未收到任務、尚在執行、執行失敗及回覆位置錯誤。

**完成條件：** 能按固定順序排查，而不是反覆重送訊息。

### 第 17 天：閱讀 Harness Log

- 找出一次成功任務的開始、處理與結束紀錄。
- 找出過去 `relay-mesh not supported` 的錯誤證據。
- 將錯誤翻譯成「哪個設定不相容」及「下一步檢查什麼」。

**完成條件：** 能從日誌提出有依據的故障判斷。

### 第 18 天：設定變更與復原

- 變更一項低風險設定並記錄變更前狀態。
- 驗證變更是否生效。
- 若結果不符預期，還原原設定並再次驗證。

**完成條件：** 每次只改一項設定，知道如何確認及復原。

### 第 19 天：訊息與回覆位置判斷

- 測試主頻道、Thread 與私訊中的任務。
- 觀察 Agent 回覆出現在哪裡。
- 練習尋找「Agent 已回覆，但我在錯誤位置查看」的情況。

**完成條件：** 能快速定位任務與回覆所屬的正確脈絡。

### 第 20 天：建立故障紀錄

- 使用「時間、操作、預期、實際、狀態、日誌、處置、結果」記錄一次問題。
- 讓另一個人只看紀錄也能理解問題。

**完成條件：** 產出一份可以重現及追蹤的故障筆記。

### 第 21 天：第三階段實戰

- 選擇一項過去的真實故障或安全的測試異常。
- 依檢查表定位原因、採取一項修正並驗證結果。

**完成條件：** 能用證據說明原因與修正結果，不用擴大權限掩蓋問題。

## 第四階段：多 Agent 協作與達人養成

### 第 22 天：設計第二個專職 Agent

- 選擇一個與 Fizz 不同的角色，例如整理員、審查員或規劃員。
- 定義名稱、職責、輸入、輸出及禁止事項。

**完成條件：** 兩個 Agent 的職責清楚且不重疊。

### 第 23 天：建立第二個 Agent

- 依角色設計建立測試 Agent。
- 設定 Runtime 與必要頻道。
- 用一個小任務驗證其行為是否符合職責。

**完成條件：** 新 Agent 能穩定完成自己的專職任務。

### 第 24 天：Agent 交接

- 先讓第一個 Agent 產出材料。
- 由人類檢查後，把材料交給第二個 Agent 審查或加工。
- 記錄交接時必須提供的上下文。

**完成條件：** 兩個 Agent 能透過明確交接共同完成一項成果。

### 第 25 天：避免 Agent 混亂

- 為不同 Agent 指定清楚的 Channel 或 Thread。
- 比較同一任務同時交給多人與依序交接的差異。
- 找出重複工作、互相矛盾及上下文遺失的風險。

**完成條件：** 能選擇適合的協作順序，避免 Agent 互相干擾。

### 第 26 天：人類決策點

- 在多 Agent 流程中設定至少兩個人工檢查點。
- 明確定義何時繼續、退回、停止或改派任務。

**完成條件：** Agent 不會在缺少人類核准時自行越過重要決策。

### 第 27 天：建立自己的 Buzz 工作流程

- 選擇一個真實但低風險的日常工作。
- 規劃 Channel、Thread、Agent、任務格式、交接及驗收。
- 在 Buzz 中完整執行一次。

**完成條件：** 該流程能重複使用，而不是一次性的聊天。

### 第 28 天：撰寫個人操作手冊

- 整理建立 Channel、設定 Agent、下任務、驗收、搜尋及故障排查步驟。
- 收錄常見錯誤與安全底線。

**完成條件：** 不依賴外部教學，也能照自己的手冊完成常用操作。

### 第 29 天：完整情境演練

- 建立工作主題與頻道。
- 指派兩個 Agent 分工完成任務。
- 人工檢查、要求修正、核准並搜尋回完整紀錄。

**完成條件：** 45 分鐘內完成流程，最後 15 分鐘指出卡點與改進方法。

### 第 30 天：操作型達人考核

- 向另一位使用者示範 Buzz 的核心操作。
- 現場建立任務、判讀 Agent 狀態並處理一個模擬異常。
- 說明一項決策是由誰、根據什麼證據做出的。

**完成條件：** 不依賴逐步指示，能安全、穩定、可追溯地完成人類與多 Agent 協作。

## 安全底線

- 私鑰如同個人印章，絕不貼進頻道、AI 提示、截圖、Issue 或 Git。
- 所有練習優先使用測試資料與低風險任務。
- 修改 Agent Runtime、Provider、權限或頻道範圍前，先記錄原設定。
- Agent 的 Reaction 不等於任務完成；必須檢查文字成果及完成條件。
- 遇到問題先看狀態與 Harness Log，不以擴大權限取代故障判斷。
